## Identity-linking strategy and trade-offs
Table `user_identities(clerk_id, firebase_uid, email)`, both unique. A purchase is stored under the id that paid; entitlement checks look at the whole linked set, so mobile-bought is premium on web and the reverse. A link is created only server-side, from the caller's own identity, when both sides have the same VERIFIED email (Clerk `verification.status = verified` AND Firebase `emailVerified = true`). The client supplies nothing.
- Pros: no data migration, mobile untouched, purchases keep their original id, unlinking is deleting one row.
- Cons: needs a Clerk API call and a Firebase lookup at link time; people with different emails on web and mobile are not linked (needs a manual row in `user_identities` or a future code-based link flow); if either side is later changed to a different email nothing re-validates the existing link; if an email is taken by two Clerk users the link is refused (`ambiguous`/`conflict`).
- Direction limit: the web backend sees the link. The Flutter app still reads `premium_members` by its own Firebase uid, so a web purchase is NOT premium inside the mobile app unless it is also written under the Firebase uid. I best-effort mirror `isPremium` to the Firestore `users/{firebase_uid}` doc for linked Firebase ids, but I did not verify the mobile app reads that. Decide whether to also upsert a `premium_members` row for the linked Firebase uid.
- Linking fires when a free web account loads the app (once per session). A mobile-only user is never linked until they open the web app.

## How a purchase works
1. `/premium` -> `POST /api/payments/order`: rate limited (5 per 10 min per user, `PAYMENT_ORDER_LIMIT`), refuses if already premium, refuses unless the PIQ in Firestore passes the server completeness check (403 `PIQ_INCOMPLETE`; the client flag `piqComplete` is ignored), amount fixed at 29900 paise, reuses an unpaid order from the last 30 min, concurrent double clicks share one in-flight call.
2. Razorpay Checkout opens with the server's order. On success the browser posts the three ids to `/api/payments/verify`: HMAC check (timing safe), order must belong to the caller or a linked id, Razorpay payment fetched to confirm order id, amount and currency, captured if only authorized, then `activate`.
3. `activate` is the single route to premium. Atomic `created|failed -> paid` update, unique `payment_id`, entitlement upserts are idempotent and re-run to heal a half-finished grant. Webhook (`payment.captured`, `order.paid`) calls the same function, so redirect-first, webhook-first and replays all end with one grant and one receipt.
4. Webhook also handles `payment.failed` (never downgrades a paid order), `refund.processed` (full refund revokes premium; partial is logged only) and dedupes on `x-razorpay-event-id`.
5. Every transition is a row in `payment_events`.
GST: `GST_RATE_PERCENT` (default 0 = none shown). If set, the price is treated as GST-inclusive and split. `BUSINESS_GSTIN` is printed when set. I did not decide whether you must charge GST, check with your accountant.

## Open issues / left for the human
- Mobile cannot see web purchases (see above).
- Disputes/chargebacks are not handled; refunds are only picked up from the webhook.
- No admin UI to manually link identities or grant access.
- `/billing` shows receipt details on screen; there is no PDF invoice.
- Rate limiting and the in-flight guard are per process; with several instances the DB uniqueness is what protects you.
- Existing webhook-replay protection keys on `x-razorpay-event-id`; if that header is missing a derived id is used.
- Test dependency `jose` is resolved transitively from node_modules (not declared in package.json).
